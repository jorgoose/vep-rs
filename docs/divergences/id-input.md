# Identifier input resolved from the cache's variation files

A difference in which identifiers resolve, on an input format no measured dataset uses; nothing is set aside.

Ensembl VEP reads an identifier list (`--format id`) only with a database connection (`Parser/ID.pm` line 100, `Cannot use ID format in offline mode`). For each name it asks the variation database, failed variants included (lines 159-162, `fetch_by_name`, whose comparison is case-insensitive and falls back to the variant synonyms and, for `ss` names, the subsnp identifiers), then the structural variation database (lines 168-173). It makes one variation feature per genomic mapping of the variant it finds, on whatever sequence region the mapping lies, renamed to the identifier as written (lines 185-191).

A name neither database knows is warned `No variant found with ID '<id>'` (line 175), and a variant with no mapping is warned `No mappings found for variant '<id>'` (line 181); both are skipped and the list goes on.

vep-rs resolves the list from the cache's variation files (`variations/<chr>/all_vars.gz`, or the per-region files of a cache dumped without the conversion step). Every name of the list is held in memory and every file is read once, start to end, so the pass costs a read of the variation data whatever the number of names.

A mapping is each variation feature of that name in the files, with the identifier as its name and its input line. The mappings come in karyotype order of their sequence regions (the chromosomes, then X, Y and MT, then the other contigs by name) and by position within one. A record the dumper wrote twice, once per failure reason of a failed variant (its query joins `failed_variation`, `AnnotationSource/Database/Variation.pm` line 175), is one mapping, as it is one feature in the database.

The files hold the variation features of every sequence region the cache carries by name, patches, alternate contigs and unplaced scaffolds included under the names the database gives them (`HSCHR21_2_CTG1_1`). So a mapping on one of those resolves like a mapping on a chromosome and is annotated against that sequence region's transcripts in the cache, or warned and skipped as any record on a sequence region the cache holds no transcripts for. A cache reduced to some chromosomes resolves a name to the mappings it still holds, and to the `No variant found` warning when it holds none.

A structural variant name (`nsv`, `esv`), a synonym, a subsnp identifier and a variant without a genomic mapping all take the `No variant found` warning. Names are matched without regard to ASCII case, as the database compares them. A cache without variation files refuses the format (`ERROR: [input] Cannot use ID format with a cache that has no variation files ...`).

A list line `0` is a name here and takes the `No variant found` warning. Ensembl VEP reads that line, Perl's false string, as no record (`Parser/ID.pm` line 146) and ends the buffer fill there (`Parser.pm` lines 186-187, `InputBuffer.pm` line 212). So a `0` after a name is dropped without a word, and one that opens a fill, the list's first line among them, ends the run with the names after it unread (`Runner.pm` lines 423-424). Its HGVS, SPDI, region and CAID parsers test the line the same way (`Parser/HGVS.pm` line 149, `Parser/SPDI.pm` line 141, `Parser/Region.pm` line 165, `Parser/CAID.pm` line 149).

Each resolved feature then goes through the record checks every format's records go through (`validate_vf`, `Parser.pm` lines 457-649), run from `Parser.pm` line 189 on the feature as `post_process_vfs` returns it (`Parser/ID.pm` line 196), a non-minimised indel minimised first (`Parser.pm` line 881). A feature that fails one is skipped with Ensembl VEP's warning quoting the identifier. The shapes that fail, met among the files' failed variants, are a start more than one past the end, an insertion whose start is not end + 1 and a reference whose length is not its span. The rules of [Records `--dont_skip` cannot keep](dont-skip-cannot-keep.md) apply to such a feature.

The empty-line warnings and the skip warnings carry Ensembl VEP's own line numbers: the list's lines are counted with empty lines and names the cache lacks, and every mapping of a name falls under the name's line (`Parser/ID.pm` line 148).

The variant class of a resolved name (`--variant_class`, the JSON `variant_class`) is read from a different place. Ensembl VEP prints the class its database stores for the variation feature (`VariationFeature.pm` line 1117, `class_SO_term` computes one only when none is stored), which the import derived from the allele string as stored. So a feature stored un-minimised (`TTTTT/TTTTTT`) is an `indel` although the feature Ensembl VEP annotates is its minimised `-/T`. The variation files carry no class, so vep-rs derives it from the stored allele string before minimisation, by the same derivation; the two differ only for a feature whose stored class is not that derivation.
